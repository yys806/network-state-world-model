## Mechanism, Results and Expected Versus Actual

The Encoder and current-observation posterior are called once for the anchor with `posterior_mode=mean`. Every candidate receives cloned identical state, graph and posterior latent. H1–H4 then run `model.one_step` with `prior_mode=mean`, `service_mode=expectation`, `model.eval()` and `torch.no_grad()`. Every subsequent action is compiled on the prior predicted state; every subsequent transition consumes the prior predicted state, graph and latent. Fingerprints H0–H4 and an H2←H0 negative substitution audit are in `recursive_feedback_audit.json`.

On the real validation anchor, all four formal action tensor families changed, their corresponding `trace.routed` path changed, and the corresponding target-family hidden latent changed. Route changed an existing Flow hop/route revision and host while preserving fixed Flow identities. Comm updated RB allocation and changed delivered service on the carrying relation; valid service outputs were finite. Comp's remaining work/progress matched the frozen rule. Mob's absolute FP32 next position and speed matched the frozen trigonometric rule. Direct observations and H1–H4 deltas are in `action_family_response.json`. A zero H1 Motion/CSI delta for some families is recorded as a downstream observation, not a failure or performance claim.

The model's expectation-mode wireless trace intentionally stores `NaN` in `outage_uniform_draw` because no random draw occurs. The finite-service assertion checks nominal rate, outage probability and actual rate, while explicitly recording this sentinel. Mob's displayed `new_position - old_position` can differ by about `3e-5 m` from the small analytic delta due to FP32 cancellation at large absolute coordinates; the acceptance compares the frozen FP32 `old_position + rule_delta` with the actual next position.

The secondary diagnostic uses explicit CPU `torch.Generator` seeds `6101–6103`, separately restarted for each CONTROL/INTERVENTION pair, with `prior_mode=sample` and `service_mode=sample`. Same candidate/seed replay, finite outputs and common initial belief passed. The single generator couples latent draws and outage draws; it does not create independently aligned substreams. This is `PAIRED_COMMON_SEED_DIAGNOSTIC`, not a risk measure or uncertainty calibration.

Serial and batched paths use one interface and agree within `1e-4` absolute tolerance on rollout tensors. Bounded CPU timing uses K=1,2,4,8, H4, one warmup and three measured repetitions, reporting medians and process memory in `cpu_batch_runtime_diagnostic.json`. It is a CPU implementation diagnostic, not a Planner deployment latency claim or Search/Learned/Hybrid choice.
