# PI-JWM 归档候选与停止门

## 当前决定

本轮先完成逻辑归档，不进行历史 Python 文件的物理迁移。原因不是“历史都要保留在核心”，而是当前存在可验证的工程阻塞：历史模块仍被脚本和测试 import，且全量测试基线不是全绿。贸然移动会让“原有失败”和“重构引入失败”无法区分。

## 逻辑归档范围

- `r3_*`、`r4_*`、`r5_*`、`r6_*`：旧阶段训练、策略和诊断路径。
- `v6_*` 至 `v11_*`：旧世界模型、selector 和规划诊断族。
- 与上述模块同名的运行脚本和测试。
- `记录/研究进展/归档/`：已经完成物理归档的旧设计和旧主文档。

2026-09-09 的自动映射识别出 211 个历史 Python 节点：94 个仍有至少一个反向 import，93 个仍有直接测试，当前正式节点对它们的反向引用为 0。逐文件大小、SHA-256、引用数和原路径回滚位置见 `registries/generated/archive_candidate_registry.csv`。

逻辑归档的含义是：文件保持原路径以保证复现和 import，但在 `CODE_INDEX.md`、文件清单和依赖图中标为 `historical`，AI 默认不把它当作当前方法。

## 进入物理迁移前必须同时满足

1. 每个候选都有原路径、目标路径、大小、SHA-256 和反向恢复路径。
2. 依赖图确认当前正式模块和入口不引用候选。
3. 所有引用候选的历史脚本、测试和证据复现入口已有兼容方案。
4. 能把环境缺失、fixture 过期、artifact 权限等基线问题与布局变化造成的问题分开。
5. 迁移前后分别运行同一组测试和索引 `--check`。
6. 用户批准具体逐文件映射后才执行。

当前这些条件没有全部满足，尤其是历史回归基线和 provenance 引用仍未闭合。因此“不移动”是本轮可核验的停止结论，不是遗漏。待条件满足后应生成 `记录/迁移/` 下的新映射和回滚证据，沿用 2026-08-16 的迁移审计方式。
